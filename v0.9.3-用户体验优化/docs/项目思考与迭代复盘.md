# 用户体验优化｜项目思考与迭代复盘

## 1. 项目起点与最终选择

本次作业要求为无人机专区的 C 端设计一个具有明确用户价值或商业价值的功能，并保证用户能完成一条闭环旅程。

我最终选择在下单选购环节新增两个功能：凑单助手、购物车按店铺批量删除。围绕这两个功能，补充加购受限反馈、金额进度联动、多店入口及异常状态。范围从进入选购页开始，到完成凑单或购物车整理、进入订单确认为止。

这个选择经历了几次调整。原因一方面来自实际操作中的发现，另一方面来自现实限制：我所在位置附近没有可体验的试点，试点附近也没有能协助体验的朋友，无法真实体验完整业务流程。同时，我没有内部业务数据、接口资料或完整购买规则。因此，我把主要精力放在能够直接观察、描述并通过原型表达清楚的任务上。

## 2. 先建立现状，再讨论新增功能

最初的工作计划是：录屏并截图 → 梳理页面与跳转 → 复刻可交互骨架 → 设计新功能及入口 → 补充 PRD 和异常状态 → 整理仓库交付。

现状梳理中，我关心三个层面：

- 页面有什么：功能入口、活动入口、商品信息和状态反馈。
- 用户怎么走：选点、选店、选规格、加购、整理购物车和进入订单确认。
- 状态如何变化：地图范围与配送状态、商品加购结果、各店起送状态。

例如，选择下单地址时可以拖动地图，下方随位置显示附近服务区；服务点具有具体地址、距离、可配送或自取、营业时间和营业状态等信息。这些发现帮助我认识到，配送与取餐涉及地点和服务能力的约束，不能只从一个页面推导完整业务。

复刻的目的是先保留原有的页面关系和操作语境，让新增功能能接回原流程，后续设计因此可以围绕具体入口讨论。

## 3. 从活动方向转向选购体验

我最初考虑“同一取餐点邀请朋友体验首单”。这个方向与试点覆盖有限的特点相联系，也可以结合有趣的分享页、纪念徽章和个人身份展示。

但继续分析后我遇到两个问题：

1. 自己无法方便地体验试点，也缺少试点附近的朋友，邀请和履约路径难以验证。
2. 分享趣味和奖励可以形成活动方案，但本次作业还需要体现问题定义、流程设计与异常处理能力。

随后我又考虑过空投柜取餐导航和客服补充。导航可以帮助用户从当前位置找到取餐柜，客服则涉及固定问答以外的咨询。但这两个方向都需要更多业务信息：柜机位置和通行条件、配送与自取关系、客服服务能力和处理权限等。

最终我将范围收敛到选购过程。原因在于这个环节可以直接反复操作，也能够围绕一个具体任务呈现入口、操作、反馈和恢复，而不依赖我尚未掌握的配送业务条件。

## 4. 从商品组合观察中定位问题

我以蜜雪冰城（海岸城店）为样本，记录了冰鲜柠檬水、三拼霸霸奶茶、芋泥鲜牛乳、柠檬红茶霸气桶的页面标签和加购表现，取样覆盖招牌、招牌加折扣、新品、折扣等情况。

| 操作观察 | 我当时得到的信息 |
| --- | --- |
| 单独加入柠檬水后，提示未满起送，需要继续加购 | 当前用户任务是补足本店起送金额 |
| 柠檬水与三拼霸霸奶茶组合受限，提示换店加购 | 换店动作不能帮助完成原店起送任务 |
| 柠檬水与柠檬红茶可以一起加入，但继续加第二杯红茶受到限制 | 商品标签不能直接解释所有组合和数量条件 |
| 芋泥鲜牛乳与另外几款商品组合可以进入可配送状态 | 不能简单将“有折扣”视为唯一限制原因 |
| 不同商品出现数量上限的时机不同 | 不能把限制统一理解为总杯数上限 |

我曾考虑这些表现是否与优惠份数、商品重量或无人机限重有关。但手中证据无法确认这些原因，所以没有继续据此设计新的业务规则。

我把结论收敛为两点：本店凑起送的任务与部分提示的下一步方向衔接不足；用户在操作前难以判断哪些选择还能继续加入。这是能够观察到的体验问题，至于限制来自什么业务条件需要另外取得信息。

并且这些记录主要集中于一家门店，不能说明所有门店都有相同问题，因此我没有把“修改这一家店的规则”作为项目的核心成果。

## 5. 从局部提示修订上升为凑单助手

早期我考虑过修改加购文案、增加当前购买状态，以及让“去加购”真正响应并高亮本店商品。进一步梳理后，我确认原入口已经能够定位到对应门店，但后续仍需用户自行寻找合适商品。

如果只解决某组商品的提示，价值容易局限于样本。因此我将核心任务改为：“本店还未达到起送金额时，帮助用户继续找到可选择的商品。”由此增加凑单助手，而将加购提示和按钮状态作为辅助流程优化。

这个变化也明确了普通加购与凑单的关系：

- 普通加购是用户向购物车加入商品的基础动作。
- 凑单是用户为了补足某店起送金额而进行的选购任务。
- 凑单助手提供筛选和金额反馈，但仍然要遵循同样的购买校验。

因此助手加入后不应让普通加购入口或原受限提示消失，已有的按店起送信息和三店一起购买能力继续沿用。

## 6. 凑单助手如何迭代

### 6.1 从组合方案卡改为推荐单品

最初的UI使用组合方案卡，先明确选择行为：已选方案可以再次点击取消，多个方案可以同时选择，点击“自己选”清空未提交选择。

随后我发现组合方案需要更复杂的计算，还容易引入数量、价格和方案之间的解释负担。结合已有竞品截图的呈现方式，我将其调整为推荐单品列表和金额筛选，入口名称由“一键凑起送”调整为“推荐凑单”。

这样可以保留用户自主选择的空间，也使计算需求更容易说明：商品按单件金额筛选，用户选择后的金额与差额实时变化，不要求系统自动寻找最优组合。

### 6.2 保持页面位置，让金额反馈随操作变化

早期原型在选择商品后重新渲染弹层，进度直接切换为“已凑满”，打断了用户的连续选择。
我要求改为原位更新：选中、取消、数量变化时，顶部数字和进度条按金额变化，弹层和滚动位置保持稳定。
这里区分了三个时刻：选择后的预览达到门槛、商品确认加入成功、实际购物车达到起送金额。

### 6.3 减少正常状态的信息负担

取消保留“当前还可加N杯”这类正常状态提示，原因考虑到容易和优惠限份混淆。
当前方案保留正常的添加动作；在确认受限时置灰添加按钮并提供原因，用户调整购物车后再动态恢复允许的操作。商品的规格查看、减购等调整手段仍保留。

### 6.4 多店场景

原来平台已有按店起送进度，因此本次新增的是任务入口和选购辅助，每家店独立计算，完成一家的凑单只移除该店入口。

## 7. 为什么增加购物车按店铺批量删除

在整理多店购物车时，我发现已有全车清空和逐项调整，但缺少一次删除某一家店商品的操作。用户放弃一店商品时，仍需要逐项减购；全车清空又会影响其他已经选好的商品。

因此我在门店分组旁增加删除入口，确认后移除目标店全部商品，同时保留其他店的商品。确认弹窗用于明确删除对象和影响范围。
删除成功后需要同步数量、金额、凑单入口和结算状态。若删除的是最后一家店，则进入空购物车状态，并提供返回选购的入口。

## 8. 异常状态如何取舍

我将正常路径放入可交互原型，异常和边界状态另用图片展示，便于逐页讨论文案和恢复动作。
最终图集包含十种状态：商品组合受限、商品暂不可售、加购失败、加购请求超时、商品删除失败、删除最后一家店后的空购物车、金额筛选空状态、购物车加载失败、按店删除处理中、按店删除请求超时。
过程中，我删除了两种不适合继续展开的展示：起送信息暂不可用和删除确认前购物车又发生变化。

其他范围也做了区分：

- 购买上限置灰和受限提示已经存在于当前原型，不重复增加异常图。
- 三家已满后再加第四家属于原产品已有边界，不纳入本次新增展示。
- 登录中断和重新登录确实可能发生，但本版不扩展登录恢复流程。
- 筛选无匹配商品时保留选项栏，下方商品区留空；已有商品受限时保留置灰行。
- 超时和失败提示采用简短文案，将重复操作保障放在系统处理要求中。

这轮取舍让我把异常设计重新放回用户任务：每个状态都要说明用户为什么停在这里、还能做什么，而不是为了覆盖分类增加页面。

## 9. 金额计算与信息边界

我单独整理了凑单金额计算规则，将商品价格、起送统计金额和最终应付金额分开讨论。

现阶段用统一的商品金额口径说明交互：本店现有金额加上助手已选金额得到预览合计再计算差额和进度。其他店金额不参与本店凑单；价格筛选按单件价格。

尚需确认的条件包括：起送按折前还是折后统计，规格差价、加料和包装费是否参与，数量变化是否影响价格，商品和购买校验结果从哪里获取，批量加购是否可能部分成功。

没有内部资料时我只说明新功能需要什么信息、用于什么判断和需要谁提供，金额足够与允许购买也分别判断，防止出现凑单功能绕过购买限制规则的bug。

## 10. 我的工作与现阶段产出

本次工作中，我完成了方向探索、现状录屏与页面梳理、样本操作记录、问题判断、功能范围收敛、交互反馈、文案修订和异常取舍。AI 用于辅助原型实现、图稿绘制和文档整理；关键取舍由我结合观察结果逐轮调整。

现阶段产出包括：可交互原型、新版 PRD、十张异常状态图及总览、金额规则讨论稿、README和复盘。

我没有获得线上转化数据，也尚未进行用户访谈或完整履约体验，当前能说明的是：两个新增功能形成了可评审的任务闭环，正常路径和异常反馈也能够对应到具体界面。

后续需要补充更多门店及商品组合的样本，确认起送与购买限制的信息来源，并围绕“完成本店凑单”“删除某店且保留其他店商品”两个任务开展可用性验证。重点关注任务完成率、重复失败、操作次数和整理耗时，再判断方案是否真正降低了选购成本。
